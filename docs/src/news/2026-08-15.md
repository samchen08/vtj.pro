# VTJ.PRO v2.7.1 发布：推出 Agent 项目级记忆系统，让 AI 真正理解项目上下文

**摘要：** 低代码开发平台 VTJ.PRO 于近日发布 v2.7.1 版本，正式上线 Agent 项目级记忆系统。该系统通过将项目规范、技术决策、避坑规则等结构化记忆跨 Topic 持久化，解决了 AI Agent 在多轮对话中“遗忘”项目约定、需重复说明的痛点，使 Agent 从“问答工具”进化为“持续参与项目演进”的开发协作者。

---

## 背景：Agent 的“遗忘”之痛

VTJ.PRO 是一个 AI 驱动的 Vue 3 低代码开发平台，其 Agent 不仅能回答问题，还能创建页面、生成区块、调用 API、修改 DSL，并通过 Architect 和 Editor 双代理协作完成长流程任务。

然而，在实际使用中，团队发现一个高频痛点：用户在某次任务中确认的约定，到了新 Topic 中又要重新告知 Agent。例如，Agent 曾因使用区块名称而非区块 ID 组装页面导致运行报错，用户明确指示“记住：页面引用区块要用区块 ID”，但这条规则在下一次新话题中再次被忽略。

单纯增大上下文窗口并不能根治这一问题——新 Topic 默认不携带旧聊天，完整历史又带来高昂的 token 成本和模型噪声。VTJ.PRO 团队认为，核心问题在于**缺乏一个与项目绑定、可跨对话复用的长期记忆机制**。

## 解决方案：项目级记忆系统

v2.7.1 引入的“项目级记忆”系统，将“对话历史”、“历史摘要”和“项目记忆”拆分为三种不同生命周期的上下文：

| 上下文 | 作用 | 生命周期 |
|--------|------|----------|
| 原始 Chat | 记录当前步骤详情 | 当前 Topic |
| 历史摘要 | 归纳长任务已完成事项 | 当前 Topic |
| **项目记忆** | **存储未来任务须遵守的规则** | **跨 Topic** |

### 核心设计原则

1. **记忆归属于项目，而非用户**  
   每条记忆绑定 `project_id`，避免将“深色科技风”等偏好错误带入其他项目。

2. **五类结构化记忆**  
   系统将可复用结论分为 `constraint`（约束）、`decision`（决策）、`preference`（偏好）、`fact`（事实）和 `pitfall`（陷阱），不保存临时进度或未验证猜测。

3. **写入与召回分离**  
   记忆仅在任务成功收尾时触发沉淀，不干扰实时对话；召回则依赖已持久化的结构化数据，确保稳定可靠。

## 关键技术亮点

### “记住：”确定性通道

在早期版本中，即便用户明确输入“记住：……”，系统仍需依赖 LLM 提取，存在漏记风险。v2.7.1 为此增加**确定性通道**：当检测到“记住：”或“请记住：”指令时，直接生成重要度为 5 的约束记忆，不经模型处理，确保用户显式意图 100% 落库。

### 手工记忆优先于自动提取

系统支持用户通过界面手工新增、编辑或停用记忆。当自动提取与手工维护出现同 key 冲突时，**手工记忆拥有更高优先级**，不会被覆盖。这体现了“用户明确维护的规则应拥有更高权威”的产品理念。

### 并发防丢机制

针对同一 Topic 多轮完成事件的并发场景，系统采用“单运行任务 + 待处理标记”策略，保证最新数据不被静默丢弃，无需引入复杂消息队列。

### 召回策略：不急于上向量库

当前项目级记忆规模通常仅有数十至数百条，VTJ.PRO 选择使用 MySQL + 规则打分（基于重要度、文件范围、关键词等）进行召回，并限制注入上下文不超过 12 条、总 token 控制在 6000 以内。团队明确表示：“技术复杂度应由数据规模和评测结果驱动，而不是由架构想象力驱动。”

### 可观测性增强

为便于调试和监控，系统在 Chat 表中新增 `memory_refs`（实际注入的记忆 ID）和 `memory_tokens`（记忆上下文估算 token 数）字段，开发者和管理员可清晰追溯每轮对话是否召回、召回了哪些记忆以及消耗了多少上下文预算。

## 安全与人工治理

考虑到记忆会被未来模型调用反复使用，系统内置了多层防护：
- 写入前自动检测密码、Token、API Key 等敏感信息并拒写。
- 过滤常见提示词注入文本（如“忽略之前的指令”）。
- 项目级 CRUD 需通过所有者、协作者或超级管理员权限校验。
- 后台管理页支持跨应用查询、编辑、启停记忆，且操作受菜单、按钮和 API 三层权限控制。
- 删除应用或来源 Topic 时，记忆随外键级联处理或置空来源引用，确保数据整洁。

## 未来规划

团队表示，当前方案有意保持简单，后续将优先补齐结构化提取审计记录（包括触发原因、模型、候选数量、过滤原因等），并建立离线召回评测集。待数据积累到一定程度，再根据实际评测结果决定是否引入向量检索、混合重排或记忆版本管理。
